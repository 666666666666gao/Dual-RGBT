# 高响应但定位错误：候选身份与状态写入的开源参考

本项目实际证据：完整dev成本0.05，在有有效GT的6430次模板更新事件中，
1053次同帧原始IoU<.1，平均置信度.818；其中593次GT中心仍在搜索ROI内。
因此实际问题不仅是源视野未覆盖，响应高也不能单独证明当前框适合作为模板。
尚未人工核查这些帧，不能把全部错误归因为相似干扰物；更新也未被证明造成后续漂移。

## 直接核到的机制

- keep_track.py:437–476 从已有backbone_feat和响应局部峰提取候选描述及全图坐标，
  向matcher提供相邻帧描述、位置和响应分数。
- candidates.py:29–79 用匹配关系传播object_id，更新所选身份，不只按单帧最高响应决定。
  第51–55行对所选目标的低匹配概率另行处理，说明响应与身份匹配分数是不同量。
- keep_track.py:183–191 的target_label_certainty仍来自score_map.max；
  classifier更新还要求flag不属于not_found/uncertain。不能声称该certainty就是真实IoU估计。
- 第628–650行以certainty和已有样本权重管理memory，第890–895行抑制低certainty样本权重；
  default.py:66–67确实启用该选项。这是在线分类样本memory，不等同于本项目双模板像素替换。

## 对本项目的实施含义

值得借鉴的是把候选身份连续性、当前响应与状态写入依据分开。
本项目可以研究用已取得的主模态候选/历史身份信息预测辅助验证价值，在昂贵辅助编码之前选择区域；
取得辅助证据后再决定定位及模板写入。该连接必须用真实查询收益和闭环结果训练与验证。
尚未实现身份关联或新的模板规则，也不复制KeepTrack阈值；它的候选匹配机制本身不是我们的新贡献。
原冻结测试与全882训练配置不改。下一项必要证据是同一训练状态下的实际主/辅助动作输出，
比较当前裁剪代理与执行后全图定位误差的收益，随后才决定最小的监督及执行修改。
