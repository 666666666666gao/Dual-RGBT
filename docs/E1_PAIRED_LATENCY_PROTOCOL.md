# 正式 E1 的完整 dev 配对延迟

旧 `compare_tracking_latency.py` 只构建 E0 `DualRGBT/Tracker`，不能加载 E1 候选策略并证明其速度。本入口独立新增，不修改现有46份训练、评估或排队源码。

## 依赖和执行顺序

`complete_candidate_latency.py --plan reports/e1_paired_latency_plan.json` 是本地唯一待启动控制器，使用现有 NumPy Python。先独立 SOURCE 审查；首次依赖观察为2026-10-15 08:38:30 BJT，仅读取 E0 补测控制器已写的本地状态并核对其身份。之后根据它的预计节点等待，至少240秒，不额外轮询正在训练的 NN。

只有 E1 与 E0 的三数据集正式管线均完整结束、全部所属原生任务 COMPLETE/exit0 后，才允许 SSH 核验封印、读取最终 E1 checkpoint 和 dev 冻结选择文件的 SHA。原 launch 函数确认物理 GPU0 显存低于500MiB；本队列只在 GPU0 上执行一个进程，不使用 GPU1 或其他卡。

先执行固定1序列×16帧的真实推理检查，严格加载同一正式权重，检查模型状态未变化及 E1 末帧严格重载后的框、路由、模板和历史逐位相同。它没有反向或优化器更新，也不是精度或正式速度结果。真实原生 exit0、收取并验证后，才能执行全部97序列/54646帧的配对测量。完整路径和检查路径使用同一入口、最终权重和冻结预算，不重新按测速选型。

每侧只用首帧初始框，之后独立维护自身搜索、模板与历史状态；不根据未来 GT 跳帧，不保存或评分 baseline 框。两模型在同一进程常驻，每帧交替先后顺序，各自解码同一原始 RGB/TIR 图片。

## 计时和结果

外层在开始前和结束后同步 CUDA。`service` 包括解码、裁剪、策略、前向、结果提取和模板更新；`tracking` 从解码结束计时，仍包含原生 tracker 的全部 CPU/GPU 工作，不称纯 GPU 内核时间。加载、哈希核验、CSV与状态写盘不计入逐帧服务时间，整段 wall time 单列。

报告全部54646帧，以及事后固定排除每序列 frame0–8 的53773帧，两侧各自的平均/P95延迟和FPS；另计54549个在线帧的动作、模态、查询和token数、模型总参数。记录两个模型常驻时的进程共享显存峰值；它不能代表两侧分别独立部署的显存占用。

固定16帧检查预计不到3分钟，首次180秒后收取；用该次实际两侧服务时间投影完整测量时长，第一次在估计结束前5分钟观察，此后根据真实进度更新预计节点，最短180秒、最长4小时。观察超时不重启任务。每次原生任务退出后收取原始CSV、config、COMPLETE和原生状态，本地逐行核对序列、帧次序、交替顺序、有限时间与服务/跟踪关系，并从CSV重算全部均值/P95/FPS和动作计数。

完整dev配对是系统开销对照；文件缓存、交替顺序和两个常驻模型仍影响测量。它不替代完整test结果，不能把全部时间差归因于单个模块、token或权重共享。现有正式三数据集测试服务时间另行保留。只有真实完整退出、独立结果审计后，才能写 E1 的效率结论。目前本文件是执行协议，无新速度数字。
